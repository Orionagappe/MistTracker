# Validator Moderator Rights — Server Autonomy Principle

**Designation**: April 26, 2026  
**Authority**: Framework governance  
**Status**: Core principle established

---

## The Principle

**Validators who pass the Lang Orrery Test earn moderator rights on their own server, whether rented or owned.**

The data generated by a validator and their peer lattice is *theirs*. Moderation authority follows data ownership.

---

## What This Establishes

### 1. Data Ownership is Foundational

A validator's claims, verdicts, audit trails, and team interactions are their intellectual and operational property. No central authority owns this data. Validators do.

**Implication**: The framework is fundamentally decentralized. There is no central MistTracker authority. There are distributed validators, each with their own data.

### 2. Moderator Rights Are Earned, Not Granted

Only validators who:
- Pass the Lang Orrery Test (prove understanding of peer lattice equilibrium)
- Maintain reputation above 70%
- Demonstrate the four emotions (clarity, integrity, courage, humility)

...earn the right to moderate *their own* server space.

**This prevents**:
- Unqualified validators controlling spaces
- Single authority appointing moderators (decentralization preserved)
- Moderators who haven't proven peer lattice understanding
- Authority consolidation

### 3. "Own Server" Definition

A validator's "own server" is any space where:
- They host the primary data (claims, verdicts, audit chain)
- They lead the peer lattice cohort
- They bear responsibility for data integrity
- They are the first point of appeal for disputes

**Rented or owned hardware**: Doesn't matter. Ownership is data responsibility, not physical possession.

**Example scenarios**:
- ✓ Validator A rents cloud server, hosts their peer lattice data → Can moderate
- ✓ Validator B owns a physical machine, runs validator node → Can moderate
- ✓ Validator C uses corporate infrastructure but is accountable → Can moderate
- ✗ Validator D uses central authority's server without accountability → Cannot moderate (data not theirs)

## Moderator Rights Defined

### What Moderators Can Do (On Their Server)

1. **Manage peer lattice membership**
   - Add new validators to cohort
   - Remove validators who violate framework principles
   - Reassign teaching responsibilities
   - Create new peer groups

2. **Enforce framework standards locally**
   - Edit claims that violate language discipline (with audit trail of edits)
   - Delete spam or off-topic content (logged on blockchain)
   - Correct audit chain entries (with full history preserved)
   - Manage access to high-sensitivity data (alien signals, etc.)

3. **Resolve peer disputes**
   - Arbitrate disagreements between validators
   - Document both sides of conflicts
   - Make binding decisions for their server (others can appeal)
   - Assign language precision standards

4. **Control server infrastructure**
   - Manage hardware/bandwidth
   - Set backup policies
   - Decide replication schedule
   - Control who can join the server

### What Moderators Cannot Do

1. **Override other validators' data**
   - Cannot delete another validator's claims (only append corrections)
   - Cannot alter blockchain records (immutable)
   - Cannot remove validators from other servers

2. **Enforce beyond their server**
   - Cannot moderate validators on other servers
   - Cannot mandate decisions for peer lattices elsewhere
   - Cannot access private data on other servers

3. **Bypass framework principles**
   - Cannot hide audit trails
   - Cannot create hidden relationships (peer lattice must be transparent)
   - Cannot make unexamined decisions (must document reasoning)

4. **Claim unilateral authority**
   - Cannot declare themselves "final authority"
   - Cannot override peer lattice consensus
   - Cannot use moderator power to accumulate reputation unfairly

## Server Architecture: Federated Network

This creates a **federated validator network**:

```
┌─────────────────────────────────────────────────────┐
│         GLOBAL VALIDATOR NETWORK (Blockchain)        │
│ (All claims, verdicts, reputation shared across all) │
└─────────────────────────────────────────────────────┘
    │              │              │              │
    ▼              ▼              ▼              ▼
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐

│ their data) │ their data) │ their data) │ their data)
│ Peer: 5    │ Peer: 7    │ Peer: 4    │ Peer: 6
│ Mods: A    │ Mods: B,E  │ Mods: C    │ Mods: D
└──────────┘  └──────────┘  └──────────┘  └──────────┘

Validator E can moderate on Server B (passed test)
Validator A moderates their own data (Server A)
Cross-server claims share blockchain (decentralized truth)
```

### How It Works

1. **Validator creates their server**
   - They are primary moderator
   - Their peer lattice cohort validates locally
   - Their claims are broadcast to blockchain

2. **Claims are replicated across network**
   - All servers receive broadcasts
   - Each server verifies signature + audit trail
   - Blockchain ensures consistency

3. **Disputes are arbitrated peer-lattice-wise**
   - If Validator A disagrees with Validator B's claim
   - Both servers' evidence is reviewed by mixed-domain team
   - Blockchain records the arbitration verdict
   - Both validators implement the verdict on their servers

4. **Reputation is global**
   - Your reputation follows you across servers
   - Below 70% on any server → auto-ejection everywhere
   - Above 70% on your server → welcome on others

## Preventing Moderator Corruption

### 1. Transparency Requirement

Every moderator action is logged:
- User added/removed (why?)
- Claim edited (what changed? why?)
- Data access (who viewed what?)
- Disputes arbitrated (reasoning recorded)

**All logs broadcast to blockchain** (public record).

### 2. Appeal Mechanism

Any validator can appeal a moderator decision to:
- Their peer lattice (local arbitration)
- Mixed-domain team from other servers (inter-server arbitration)
- Global validator council if reputation at stake

**Moderator power is checked by transparency + appeal.**

### 3. Moderator Review

Every year, moderators are re-evaluated:
- Do they still pass Lang Orrery Test principles?
- Do their audit logs show reasonable decisions?
- Have any appeals been upheld against them?
- Do they maintain reputation above 70%?

**Failure to re-validate → moderator rights revoked.**

### 4. Multiple Moderators Per Server

No single moderator controls a server:
- If your server has 8 validators, up to 3-4 can be co-moderators
- Major decisions require 2+ moderator consensus
- Disagreement between moderators is arbitrated by peer lattice

**Co-moderation prevents single-point-of-failure corruption.**

## Moderator Responsibilities

Moderators are custodians, not rulers.

**Responsibility to**:
- Maintain data integrity (audit chains, backups)
- Preserve privacy (access controls working)
- Enforce standards (language discipline, framework principles)
- Facilitate arbitration (fair dispute resolution)
- Implement verdicts (from peer lattice and cross-server teams)
- Report regularly (share logs with network)

**Responsibility NOT to**:
- Accumulate power
- Hide decisions
- Override democratic process
- Create unexamined dependencies
- Use position for personal advantage

## Certification: Server Moderator

**Requirement to become server moderator**:
1. Pass Lang Orrery Test (Gold level preferred)
2. Maintain 75%+ reputation for 6 months
3. Demonstrate all four emotions through verdicts
4. Pass "Moderator Integrity" exam (understand what moderation allows/forbids)
5. Co-moderate with existing moderator for 3 months (apprenticeship)

**Annual recertification**: Re-test on framework principles, review appeal logs.
